## ۱. ثبت تغییر محدوده (Scope Change)

طبق پروپوزال §۲.۴، «اعلان/نوتیفیکیشن (پیامک/ایمیل)» خارج از محدوده بود. با درخواست صاحب پروژه، **ارسال پیامک ادمین به هنرجویان** به‌عنوان فیچر **F7** به دامنه اضافه شد و در فاز **MVP-3** (پس از فاز مالی MVP-2) پیاده‌سازی می‌شود.

**تصمیمات تأییدشده با صاحب پروژه:**

| # | موضوع | تصمیم | نکته |
|---|---|---|---|
| ۱ | زمان‌بندی | **MVP-3** — بعد از تحویل MVP-1 و MVP-2 | فیلتر «بدهکاران» به داده مالی وابسته است → ترتیب فازها منطقی است |
| ۲ | مدل ارسال | **قالب‌های آماده + ارسال دستی** | عنوان‌های مختلف = قالب‌های ذخیره‌شده با متغیر؛ متن قبل از ارسال قابل ویرایش |
| ۳ | سرویس‌دهنده | **کاوه‌نگار** | Adapter مستقل؛ فراخوانی REST با `fetch` داخلی Node، بدون SDK اختصاصی |
| ۴ | گیرندگان | **تک‌تک + گروه‌ها + فیلترهای هوشمند** | کامل‌ترین حالت — جزئیات در §۵ |

**خارج از محدوده F7 (تصمیم‌گیری آگاهانه):**
- ❌ ارسال خودکار رویدادمحور (پیامک فوری بعد از ثبت غیبت، یادآوری شب قبل کلاس و…) — **انتخاب نشد**؛ اگر بعداً خواسته شود به‌عنوان F7+ با cron/صف اضافه می‌شود
- ❌ دریافت پیامک دوطرفه / پاسخ هنرجو
- ❌ پیامک به اساتید
- ❌ OTP / ورود با پیامک

## ۲. User Stories و Acceptance Criteria

### F7-1 — مدیریت قالب‌ها

**User Story:** به عنوان ادمین، می‌خواهم قالب‌های پیامکی با عنوان‌های مختلف تعریف کنم تا پیام‌های پرتکرار را سریع و یکدست بفرستم.

- **AC1:** ادمین می‌تواند قالب با «عنوان» (یکتا) و «متن» ایجاد، ویرایش و غیرفعال کند.
- **AC2:** متن قالب از **متغیرها** پشتیبانی می‌کند (جدول §۴) که هنگام ارسال با داده واقعی هر گیرنده جایگزین می‌شود.
- **AC3:** در فرم ویرایش قالب، متغیرها با کلیک قابل درج در متن هستند (بدون تایپ دستی براکت‌ها).
- **AC4:** قالبِ غیرفعال در لیست انتخاب هنگام ارسال نمایش داده نمی‌شود ولی سابقه پیام‌های قبلی‌اش سالم می‌ماند.

### F7-2 — ارسال پیامک

**User Story:** به عنوان ادمین، می‌خواهم گیرندگان را (تک‌تک یا گروهی یا با فیلتر هوشمند) انتخاب کنم، قالب را بردارم، در صورت نیاز ویرایش کنم و بفرستم.

- **AC1:** انتخاب گیرنده به ۵ شیوه: **تک‌تک** (جستجوی هنرجو) · **کلاس** · **ساز** · **همه هنرجوهای فعال** · **فیلتر هوشمند** (§۵).
- **AC2:** فقط هنرجوهای فعال قابل انتخاب‌اند (هم‌راستا با F2-AC8).
- **AC3:** انتخاب شماره مقصد: «شماره خود هنرجو» یا «شماره قوم نزدیک» — پیش‌فرض از تنظیمات.
- **AC4:** پس از انتخاب قالب، متن در ویرایشگر بارگذاری و **قابل ویرایش** است (قالب فقط نقطه شروع است).
- **AC5:** پیش‌نمایش پیام با داده واقعی گیرنده نمونه (متغیرها جایگزین‌شده) قبل از ارسال نمایش داده می‌شود.
- **AC6:** تعداد گیرنده نهایی و هشدار «ارسال گروهی قابل بازگشت نیست» قبل از ارسال نمایش داده می‌شود (تأیید صریح).
- **AC7:** هنرجوهای بدون شماره معتبر از ارسال حذف و به ادمین گزارش می‌شوند.
- **AC8:** هر ارسال (حتی تک‌نفره) به‌صورت یک «دسته ارسال» با تمام پیام‌های تک‌تک ثبت می‌شود (audit کامل).

### F7-3 — تاریخچه و وضعیت تحویل

**User Story:** به عنوان ادمین، می‌خواهم تاریخچه ارسال‌ها و وضعیت تحویل را ببینم و پیام‌های ناموفق را دوباره بفرستم.

- **AC1:** لیست دسته‌های ارسال: تاریخ، عنوان، گیرندگان (نوع + تعداد)، خلاصه وضعیت (تحویل/ارسال/ناموفق)، ارسال‌کننده.
- **AC2:** جزئیات هر دسته: وضعیت تک‌تک پیام‌ها (هنرجو، شماره، وضعیت، زمان).
- **AC3:** همگام‌سازی وضعیت تحویل از سرویس‌دهنده (دکمه «به‌روزرسانی وضعیت» + هنگام مشاهده جزئیات).
- **AC4:** بازارسال پیام‌های ناموفق با یک کلیک.
- **AC5:** در پروفایل هر هنرجو، تاریخچه پیامک‌های او نمایش داده می‌شود (مثل تاریخچه حضور و غیاب).

### F7-4 — اتصال سرویس‌دهنده

**User Story:** به عنوان ادمین، می‌خواهم سرویس پیامکی را با API Key و شماره خط پیکربندی و تست کنم.

- **AC1:** صفحه تنظیمات، بخش «سرویس پیامکی»: انتخاب سرویس‌دهنده، API Key (ماسک‌شده)، شماره خط، شماره پیش‌فرض گیرنده.
- **AC2:** دکمه «تست اتصال» — ارسال پیام آزمایشی به شماره دلخواه.
- **AC3:** نمایش موجودی/اعتبار حساب در صورت پشتیبانی API سرویس‌دهنده.
- **AC4:** API Key فقط سمت سرور ذخیره و استفاده می‌شود؛ در UI همیشه ماسک است.

## ۳. طراحی دیتابیس (افزوده بر `03-database-design.md`)

> مدل‌ها از الان در `prisma/schema.prisma` هستند (مثل MVP-2) تا فاز MVP-3 بدون مایگریشن ساختاری شروع شود. مایگریشن و پیاده‌سازی در همان فاز.

| مدل | فیلدهای کلیدی | نکته طراحی |
|---|---|---|
| `SmsTemplate` | `title` یکتا، `body`، `isActive` | متن قالب با متغیرهای `{نام هنرجو}` و… |
| `SmsBatch` | `label`، `audienceType`، `audienceRef`، `totalCount`، `sentById` | **هر عمل ارسال = یک دسته** (حتی تک‌نفره) — audit یکنواخت |
| `SmsMessage` | `batchId`، `studentId`، `phone`، `phoneTarget`، `templateId?`، `body`، `status`، `providerRef?` | `body` = **Snapshot متن نهایی** (متغیرها جایگزین‌شده) — چون قالب‌ها بعداً تغییر می‌کنند، پیام ارسال‌شده نباید عوض شود |

**Enums جدید:** `SmsStatus` (PENDING/SENT/DELIVERED/FAILED) · `SmsAudienceType` (INDIVIDUAL/CLASS/INSTRUMENT/ALL_ACTIVE/DYNAMIC) · `SmsRecipientPhone` (STUDENT/GUARDIAN)

**فیلدهای جدید `SchoolSettings`:** `smsProvider` · `smsApiKey` 🔐 · `smsSenderLine` · `smsDefaultPhoneTarget`

**ایندکس‌ها:** `(studentId, createdAt)` برای تاریخچه پروفایل هنرجو · `(status)` برای یافتن ناموفق‌ها · `(createdAt)` برای لیست تاریخچه.

## ۴. متغیرهای قالب

| متغیر | توضیح | وابستگی |
|---|---|---|
| `{نام هنرجو}` | نام و نام‌خانوادگی گیرنده | — |
| `{نام آموزشگاه}` | از SchoolSettings | — |
| `{نام کلاس}` / `{نام استاد}` / `{روز کلاس}` / `{ساعت کلاس}` | در ارسال گروهیِ «کلاس» از کلاس مرتبط؛ در ارسال تک‌نفره از کلاس فعال هنرجو | F4 |
| `{تاریخ سررسید}` / `{مبلغ}` | اطلاعات قسط | **MVP-2** |

> نکته پیامک فارسی: هر بخش پیامک یونیکد ۷۰ کاراکتر است؛ پیام‌های طولانی چند‌بخشی و پرهزینه‌ترند. در پیش‌نمایش ارسال، «تعداد گیرنده × تعداد بخش» نمایش داده می‌شود.

## ۵. فیلترهای هوشمند گیرندگان (Audience)

| فیلتر | تعریف دقیق (کوئری) | وابستگی |
|---|---|---|
| غایبان امروز | هنرجوهایی که امروز `Attendance.status = ABSENT` دارند | F5 |
| بدهکاران | هنرجوهای دارای قسط سررسیدگذشته پرداخت‌نشده | **MVP-2** |
| بدون کلاس فعال | هنرجوی فعال بدون `Enrollment` فعال در ترم فعال | F4 |

فهرست فیلترها گسترش‌پذیر است؛ هر فیلتر در سرویس به‌صورت تابعی خالص (Date → Student[]) تعریف می‌شود.

## ۶. طراحی سرویس — الگوی Adapter (مستقل از سرویس‌دهنده)

```ts
interface SmsProviderAdapter {
  readonly id: string; // "kavenegar" | "ghasedak" | ... (بر اساس تنظیمات)
  sendToMany(p: { numbers: string[]; text: string; senderLine?: string }):
    Promise<{ ref: string; ok: boolean; error?: string }[]>; // به‌ترتیب اعداد ورودی
  getMessageStatus(ref: string): Promise<"PENDING" | "SENT" | "DELIVERED" | "FAILED">;
  getCredit(): Promise<number | null>;
}
```

- **MockSmsProvider** فقط برای توسعه/آزمایش؛ `providerRef` ساختگی با پیشوند `mock-` دارد.
- **KavenegarAdapter** از REST API با `fetch` داخلی استفاده می‌کند؛ نصب SDK کاوه‌نگار لازم نیست.
- تنظیمات Provider در `SchoolSettings` (دیتابیس) است؛ فعلاً فرم مدیریت اتصال در UI وجود ندارد و کلید کاوه‌نگار در `.env` لازم نیست.
- اگر `smsSenderLine` خالی باشد، پارامتر `sender` فرستاده نمی‌شود و خط پیش‌فرض حساب کاوه‌نگار استفاده می‌شود؛ باید در پنل حساب فعال و مجاز باشد.
- جریان ارسال: ساخت `SmsBatch` → ساخت `SmsMessage`ها (PENDING) → فراخوانی Adapter → ثبت `providerRef`/خطا → به‌روزرسانی وضعیت.
- شماره موبایل مقصد قبل از ارسال اعتبارسنجی می‌شود؛ برای تست واقعی فقط یک پیام به شماره تحت کنترل خودتان بفرستید.

## ۸. نکات عملیاتی باقی‌مانده

| مورد | شرح |
|---|---|
| سرویس‌دهنده | کاوه‌نگار REST فعال است؛ Providerهای دیگر در صورت نیاز Adapter جداگانه می‌گیرند. |
| خط فرستنده | باید در پنل کاوه‌نگار برای ارسال API و مقصد موردنظر مجاز باشد؛ «فعال» بودن یک خط به‌تنهایی تضمین پذیرش آن نیست. اگر `smsSenderLine` خالی باشد، API از فرستنده پیش‌فرض حساب استفاده می‌کند. |
| شماره پیش‌فرض گیرنده | از `smsDefaultPhoneTarget` می‌آید؛ فعلاً پیش‌فرض هنرجو (`STUDENT`). |
| نمایش اعتبار | Adapter متد `getCredit()` دارد؛ نمایش موجودی در UI هنوز پیاده نشده است. |
