# تحلیل بخش «گزارشات» — پیشنهاد بدون کدنویسی

> وضعیت: بررسی اولیه (Pre-Implementation) — کدنویسی بعد از شفاف‌سازی و تأیید شما
> تاریخ: ۱۴۰۴/۰۶/۲۶ — نویسنده: منتور مهندسی (نقش توافق‌شده)

---

## ۱) هدف بخش گزارشات چیست؟

**یک ورودی در سایدبار به نام «گزارشات»** که مدیر آموزشگاه در ۳۰ ثانیه بفهمد:
- چقدر شهریه گرفته‌ایم (ورودی) / چقدر حقوق داده‌ایم (خروجی) / سود خالص چقدر است؟
- روند مالی صعودی است یا نزولی؟ کدام ماه/ترم بهتر بود؟
- جزئیات هر تراکنش قابل جستجو و قابل خروجی (Excel/PDF) باشد.

> اصل منتور: گزارشات «ابزار تصمیم» هستند نه «جدول زیبا». هر نمودار باید به یک سوال مدیریتی پاسخ دهد.

## ۲) دارایی داده‌ای فعلی — چه داریم، چه نداریم؟

| منبع داده | جدول Prisma | وضعیت | قابل گزارش؟ |
|---|---|---|---|
| **فیش شهریه هنرجو** | `StudentReceipt` (imageUrl, amount, paidAt, note) | ✅ پیاده و پر از داده تستی | بله — درآمد واقعی فعلی همین است |
| **فیش حقوق استاد** | `TeacherReceipt` (amount, paidAt, note) + card/sheba | ✅ تازه پیاده شد | بله — هزینه حقوق فعلی همین است |
| **فاکتور/قسط/پرداخت** | `Invoice`, `Installment`, `Payment`, `PaymentInstallment` | 🟡 اسکیما آماده، **پیاده نشده** (MVP-2) | در آینده: گزارش بدهکاران، اقساط سررسید، مانده |
| **کلاس/جلسه/حضور** | `Class`, `ClassSession`, `Attendance`, `Enrollment` | ✅ کامل | بله — برای گزارش‌های غیرمالی |
| **ترم/ساز/اتاق** | `Term`, `Instrument`, `Room` | ✅ | بله — بُعدهای تحلیلی (per-Term, per-Instrument) |

**نتیجه کلیدی:** تا قبل از MVP-2، «گزارش مالی» = مجموع `StudentReceipt` منهای `TeacherReceipt`. بعد از MVP-2 باید دو لایه داشته باشیم:
- **لایه ۱ — نقدی (Cash):** فیش‌های واقعی (همین الان)
- **لایه ۲ — تعهدی (Accrual):** فاکتور/اقساط (طلب از هنرجو حتی اگر هنوز فیش نیامده)

## ۳) پیشنهاد ساختار سایدبار

```
گزارشات  ← گروه جدید
 ├─ نمای کلی مالی         /reports              (KPI + ۳ نمودار اصلی)
 ├─ درآمد — شهریه‌ها     /reports/income       (لیست فیش هنرجویان + فیلتر)
 ├─ هزینه — حقوق اساتید  /reports/expenses     (لیست فیش اساتید + فیلتر)
 └─ صورت سود و زیان       /reports/profit-loss  (درآمد - هزینه به تفکیک ماه/ترم)
```

**چرا ۴ آیتم نه ۱ آیتم؟** تجربه: مدیر ۸۰٪ مواقع فقط «نمای کلی» را می‌بیند؛ ۲۰٪ مواقع می‌خواهد «جزئیات یک فیش» را پیدا کند. تفکیک = سرعت.

آیکون پیشنهادی: `BarChart3` برای گروه، `TrendingUp/TrendingDown/Scale` برای زیرآیتم‌ها (از lucide-react موجود).

## ۴) نمای کلی مالی (/reports) — چه می‌بیند؟

### کارت‌های KPI (بالای صفحه)
| کارت | فرمول | سوال مدیریتی |
|---|---|---|
| **درآمد دوره** | SUM(StudentReceipt.amount) در بازه | این ماه چقدر گرفتیم؟ |
| **هزینه حقوق دوره** | SUM(TeacherReceipt.amount) در بازه | چقدر حقوق دادیم؟ |
| **سود خالص** | درآمد - هزینه | تهش چقدر ماند؟ |
| **میانگین فیش شهریه** | درآمد / تعداد فیش | شهریه‌ها در حال گران‌شدن؟ |
| **تعداد تراکنش‌ها** | count هر دو | حجم کاری مالی |

همه مبالغ با `toPersianDigits` + تومان.

### نمودارها (۳ نمودار — نه بیشتر در MVP)
1. **نمودار میله‌ای ماهانه — درآمد vs هزینه vs سود** (BarChart)
   - محور X: ماه شمسی (۱۴۰۴/۰۱ ... ۱۴۰۴/۰۶)
   - محور Y: تومان
   - قابلیت سوئیچ: `ماهانه / ترمی / سالانه`

2. **نمودار خطی روند تجمعی** (AreaChart)
   - مجموع تجمعی درآمد و سود از ابتدای سال — «آیا داریم رشد می‌کنیم؟»

3. **نمودار دایره‌ای تفکیک**
   - تب ۱: درآمد به تفکیک ساز (پیانو ۴۰٪، گیتار ۳۰٪ ...)
   - تب ۲: هزینه به تفکیک استاد

> کتابخانه پیشنهادی: **Recharts** (سبک، SSR-friendly، قبلاً در اکوسیستم Next.js جاافتاده) — جایگزین سبک‌تر Tremor هم OK است. از Chart.js پرهیز (حجم + عدم RTL بهینه).

## ۵) صفحات جزئیات

### /reports/income — درآمد شهریه‌ها
- جدول: تاریخ شمسی | هنرجو (لینک به پروفایل) | ساز | مبلغ | توضیح | پیش‌نمایش فیش
- فیلترها: بازه تاریخ (از/تا شمسی)، هنرجو، ساز، مبلغ (از/تا)، جستجو توضیح
- مرتب‌سازی: جدیدترین اول
- جمع صفحه: «جمع فیلترشده: ۱۲,۵۰۰,۰۰۰ تومان (۲۳ فیش)»
- خروجی: Excel + چاپ

### /reports/expenses — حقوق اساتید
- مشابه بالا ولی ستون استاد + کارت/شبا ماسک‌شده (نمایش کامل فقط با کلیک — امنیت)
- فیلتر: استاد، بازه، مبلغ

### /reports/profit-loss — صورت سود و زیان
- جدول ماهانه: ماه | درآمد | هزینه | سود | حاشیه سود٪
- سطر جمع کل
- نمودار میله‌ای همین جدول (همگام)

## ۶) فیلتر بازه زمانی — مهم‌ترین تصمیم UX

| گزینه | توضیح | پیشنهاد |
|---|---|---|
| **ماه شمسی** (پیش‌فرض) | ۱۴۰۴/۰۶/۰۱ تا ۱۴۰۴/۰۶/۳۱ | ✅ پیش‌فرض «ماه جاری» + دکمه‌های «ماه قبل/بعد» |

| **بازه دلخواه** | DatePicker شمسی (از/تا) | ✅ برای حسابرسی |
| **سال شمسی** | ۱۴۰۴ | برای نمودار سالانه |

## ۷) پیشنهادهای فراتر از مالی (بر اساس نیاز پروژه)

چون گفتی «موارد دیگه هم پیشنهاد بده»، این‌ها با داده فعلی بدون توسعه اضافی قابل‌نمودار هستند — فاز ۲ گزارشات:

| گزارش | ارزش مدیریتی | داده |
|---|---|---|
| **حضور و غیاب** — نرخ غیبت ماهانه/کلاسی | کدام کلاس افت کرده؟ | Attendance |
| **اشغال کلاس** — تعداد هنرجو per کلاس / ظرفیت اتاق | کدام کلاس خالی است؟ | Enrollment + Class |
| **کارکرد استاد** — جلسات برگزار شده per استاد | حقوق با کارکرد می‌خواند؟ | ClassSession |
| **جذب هنرجو** — ثبت‌نام ماهانه + کانال آشنایی | اینستاگرام می‌ارزد؟ | Student.referralSource |
| **وضعیت اتاق** — ساعت اشغال per اتاق | نیاز به اتاق جدید؟ | ClassSession + Room |
| **بدهکاران (پس از MVP-2)** | چه کسی قسط عقب دارد؟ | Installment.dueDate vs Payment |

**توصیه منتور:** این ۶ مورد را الان نسازیم؛ فقط در نمای کلی یک کارت «به‌زودی» بگذاریم تا ذهن مدیر آماده شود. MVP گزارشات = فقط ۴ صفحه مالی بالا.

## ۸) ملاحظات فنی (برای وقتی وارد کد شدیم)

- **کوئری:** همه گزارشات `read-only` → ماژول `reports` با `repositories/report.repository.ts` + `services/report.service.ts` (بدون actions) — مطابق قرارداد لایه‌بندی. از `prisma.$queryRaw` برای groupBy ماهانه استفاده (performance ۱۰× بهتر از JS).
- **ایندکس:** `paidAt` روی هر دو Receipt قبلاً هست؛ برای MVP کافی است. اگر تراکنش >۱۰k شد، `@@index([paidAt, amount])` اضافه می‌کنیم.
- **کش:** `revalidatePath` لازم نیست (GET)؛ از `unstable_cache` با ۶۰ ثانیه یا `force-dynamic` + پارامتر بازه استفاده.
- **امنیت:** همه `/reports/*` با `requireAdmin()` — فیش حقوق حساس است.
- **خروجی Excel:** `exceljs` سمت سرور (نه کلاینت) — یک endpoint `GET /reports/export?type=income&from=...`.
- **چاپ:** CSS print + دکمه «چاپ» که جدول فیلترشده را پرینت می‌کند (نیاز کاربر ایرانی).
- **RTL نمودار:** Recharts با `direction: rtl` + اعداد فارسی — تست دستی لازم.
- **Empty state:** اگر بازه خالی بود: «تراکنشی در این بازه نیست — بازه را تغییر دهید» نه جدول خالی.

## ۹) نقشه راه پیشنهادی (۳ گام، هر گام قابل تحویل مستقل)

**گام ۱ — MVP گزارشات (همین تسک، ~۲ روز):**
- گروه سایدبار + ۴ صفحه بالا + ۳ نمودار + فیلتر ماه/ترم/بازه + جمع‌ها + Excel
- DoD: `typecheck + build سبز · تست Vitest برای سرویس تجمیع · اسکرین‌شات چاپ · زیپ`

**گام ۲ — بدهکاران (بعد از MVP-2 مالی):**
- گزارش اقساط سررسید + مانده هر هنرجو + نمودار وصول

**گام ۳ — گزارش‌های آموزشی:**
- ۶ گزارش جدول بالا — هر کدام یک کارت + نمودار

## ۱۰) سوالات شفاف‌ساز — قبل از کدنویسی باید جواب بگیریم

> لطفاً به این ۴ سوال جواب کوتاه بده تا گام ۱ را دقیق ببندیم:

**Q1 — حقوق اساتید «سرِ ماه» ثابت است یا متغیر؟**
- A) ثابت ماهانه (مثل ۱۵م هر ماه یک فیش)
- B) بر اساس تعداد جلسات برگزار شده (حق‌التدریس ساعتی)
- C) ترکیبی — بعضی ثابت، بعضی ساعتی

**Q2 — مبنای درآمد چیست؟**
- A) فقط `StudentReceipt` (وضع فعلی — ساده)
- B) `StudentReceipt` + `Invoice/Installment` (بعد از MVP-2 باید بدهکاران هم بیاید)

**Q3 — بازه پیش‌فرض و خروجی؟**
- پیش‌فرض: ماه شمسی جاری یا ترم فعال؟ خروجی Excel لازم است یا فعلاً فقط نمایش + چاپ کافی است؟

**Q4 — سود خالص را می‌خواهی؟**
- آیا «سود = شهریه - حقوق» کافی است یا هزینه‌های دیگر (اجاره، قبض) هم بعداً اضافه می‌شود؟ (اگر بله، یک جدول `Expense` عمومی در آینده لازم داریم)

## ۱۱) تصمیم نهایی — پاسخ شما (۱۴۰۴/۰۶/۲۶)

| سوال | پاسخ شما | تفسیر |
|---|---|---|
| Q1 حقوق | **مختلط — بعضی ثابت، بعضی ساعتی** | گزارش فعلی فقط جمع فیش‌هاست (فرقی نمی‌کند)، ولی در طراحی باید هر استاد «نوع حقوق» داشته باشد تا فاز بعد محاسبه خودکار شود |
| Q2 درآمد | **فیش + فاکتور/قسط (با MVP-2)** | MVP گزارشات با StudentReceipt می‌آید + جای خالی بدهکاران از الان تعبیه می‌شود |
| Q3 بازه/خروجی | **ماه جاری + سوئیچ ترم/بازه دلخواه + Excel و چاپ** | فیلتر ۳ حالته + دکمه Excel + چاپ |
| Q4 سود | **الان ساده (شهریه-حقوق)، بعداً هزینه عمومی** | الان Profit = Income-Expense، آینده + جدول Expense |

> این یعنی: گام ۱ بدون تغییر می‌ماند (سریع)، ولی اسکیما/سرویس را طوری می‌چینیم که گام ۲ و ۳ بدون بازنویسی اضافه شوند.

## ۱۲) پیامد پاسخ «مختلط» و «فیش+فاکتور» بر طراحی

### چرا الان مشکلی ایجاد نمی‌کند؟
گزارشات **فقط جمع فیش‌های ثبت‌شده** را نشان می‌دهند — فرقی نمی‌کند حقوق استاد ثابت باشد یا ساعتی؛ هر دو یک `TeacherReceipt` با مبلغ و تاریخ هستند. پس گام ۱ بدون نیاز به منطق محاسباتی جدید قابل تحویل است.

### چه چیزی برای آینده باید از الان پیش‌بینی شود؟

1. **نوع حقوق استاد (برای گام ۲):**
   - پیشنهاد فیلد آینده روی `Teacher`: `salaryType: FIXED | HOURLY | MIXED`, `fixedAmount?`, `hourlyRate?`
   - در گزارشات فاز بعد: ستون «مبلغ مورد انتظار vs پرداخت‌شده» + هشدار مغایرت ساعتی
   - **فعلاً نمی‌سازیم** — فقط در سرویس گزارش یک `TODO` و یک کارت «به‌زودی: مغایرت حقوق ساعتی»

2. **بدهکاران (برای بعد از MVP-2):**
   - وقتی `Invoice/Installment/Payment` پیاده شد، گزارش «بدهکاران» = `SUM(Installment.amount where dueDate < today) - SUM(Payment)` 
   - در گام ۱: کارت «بدهکاران — به‌زودی (پس از فاز مالی)» + لینک غیرفعال در سایدبار (badge: به‌زودی)

3. **هزینه‌های عمومی (اجاره/قبض):**
   - جدول آینده `Expense { id, title, amount, paidAt, category }` — مثل Receipt ولی بدون استاد
   - سود آینده = `شهریه - (حقوق + هزینه عمومی)`
   - در گام ۱: فرمول ساده `profit = income - teacherCost` + یادداشت «هزینه‌های عمومی در فاز بعد»

### نقشه راه نهایی (تأیید شده با پاسخ شما)

| گام | محدوده | خروجی |
|---|---|---|
| **گام ۱ — الان** | فقط فیش‌ها + ماه/ترم/بازه + Excel/چاپ + سود ساده | ۴ صفحه + ۳ نمودار — قابل تحویل در ۲ روز |
| **گام ۲ — پس از MVP-2** | + بدهکاران/وصول + مغایرت حقوق مختلط | ۲ صفحه جدید بدون بازنویسی گام ۱ |
| **گام ۳ — هزینه عمومی** | + جدول Expense + سود کامل | ۱ صفحه + به‌روزرسانی فرمول سود |
