# پروپوزال پروژه: سامانه مدیریت آموزشگاه موسیقی (MVP)

**نسخه سند:** ۱.۰
**تاریخ:** آذر ۱۴۰۴ (سپتامبر ۲۰۲۶)
**وضعیت:** پیش‌نویس اولیه — در انتظار تأیید نهایی

---

## ۱. معرفی و هدف پروژه

توسعه‌ی یک وب‌اپلیکیشن اختصاصی برای مدیریت داخلی یک آموزشگاه موسیقی واقعی (نه یک محصول عمومی/SaaS). هدف اصلی نسخه اول (MVP)، جایگزین کردن فرآیندهای دستی/سنتی مدیریت آموزشگاه (ثبت هنرجو، تخصیص استاد، برنامه‌ریزی کلاسی و حضور و غیاب) با یک پنل مدیریتی متمرکز است.

این پروژه به‌صورت **واقعی در آموزشگاه استفاده خواهد شد**، بنابراین باید با کیفیت و پایداری قابل قبول برای محیط پروداکشن توسعه یابد؛ صرفاً یک پروژه تمرینی نیست.

## ۲. محدوده پروژه (Scope)

پروژه در دو فاز پیاپی توسعه می‌یابد:

### ۲.۱ MVP-1 — نسخه اولیه (هدف: کمتر از ۱ ماه)
| # | فیچر | توضیح |
|---|---|---|
| 0 | مدیریت ترم تحصیلی | تعریف ترم با تاریخ شروع/پایان |
| 1 | مدیریت هنرجویان | پروفایل کامل هنرجو (بخش ۲.۳) |
| 2 | مدیریت اساتید و سازها/دوره‌ها | هر استاد به یک یا چند ساز مرتبط می‌شود |
| 3 | **زمان‌بندی و برنامه کلاسی** (فیچر هسته‌ای) | تعریف کلاس، تخصیص هنرجو/استاد/اتاق/زمان |
| 4 | حضور و غیاب | ثبت حضور/غیاب هنرجو در هر جلسه برگزارشده |
| 5 | احراز هویت ادمین | ورود امن پنل مدیریت |

### ۲.۲ MVP-2 — بلافاصله پس از MVP-1
| # | فیچر | توضیح |
|---|---|---|
| 6 | **مدیریت مالی کامل** | مبلغ شهریه، پرداخت قسطی، تاریخچه پرداخت، بدهی، فاکتور |

> **تصمیم مدیریت محدوده:** در ابتدا «مدیریت مالی» کاملاً خارج از دامنه در نظر گرفته شده بود، اما پس از بازبینی نیازمندی‌ها مشخص شد که پروفایل هنرجو باید وضعیت مالی را نیز شامل شود. از آنجا که مدیریت مالی کامل (قسط/بدهی/فاکتور) به‌تنهایی حجم کاری هم‌تراز با فیچر زمان‌بندی دارد و افزودن مستقیم آن به MVP-1 با محدودیت زمانی «کمتر از ۱ ماه» و توسعه‌ی تک‌نفره در تضاد است، **به‌جای فشرده‌سازی همه‌چیز در یک فاز، آن را به فاز مجزای MVP-2 منتقل کردیم که بلافاصله پس از تحویل MVP-1 آغاز می‌شود.**

### ۲.۳ پروفایل هنرجو — فیلدهای کامل
| فیلد | توضیح |
|---|---|
| نام و نام‌خانوادگی | الزامی |
| کد ملی | الزامی |
| ساز(های) آموزشی | یک هنرجو می‌تواند هم‌زمان چند ساز یاد بگیرد |
| شماره تماس | شماره خودش + شماره یک نفر از اقوام نزدیک (الزامی) |
| آدرس | اختیاری |
| تاریخ ثبت‌نام | الزامی |
| وضعیت مالی/شهریه | در MVP-2 اضافه می‌شود (بخش ۲.۲) |
| نحوه آشنایی با آموزشگاه | مثلاً: معرفی دوستان، اینستاگرام، تابلو، و... |

> «نوع کلاس‌های هنرجو» و «تعداد جلسات گذشته/باقی‌مانده از ترم» **فیلد مستقل نیستند** — این‌ها مقادیر مشتق‌شده (Derived) از رکوردهای ثبت‌نام کلاس (F4) و تقویم ترم (F0) هستند و به‌صورت خودکار محاسبه می‌شوند، نه ورودی دستی.

### ۲.۴ خارج از محدوده (فازهای دورتر آینده)
- پنل اختصاصی استاد (ورود مستقل استاد به سیستم)
- پنل اختصاصی هنرجو/والدین
- گزارش‌گیری و داشبورد تحلیلی پیشرفته
- محدودیت ظرفیت کلاس‌های گروهی
- اعلان/نوتیفیکیشن (پیامک/ایمیل)

> **نکته معماری مهم:** با اینکه پنل استاد و هنرجو در این فازها نیست، مدل داده (دیتابیس) از ابتدا طوری طراحی می‌شود که افزودن این نقش‌ها در آینده نیاز به بازطراحی اساسی نداشته باشد.

## ۳. کاربران و نقش‌ها

| نقش | دسترسی در MVP |
|---|---|
| **ادمین/مدیر آموزشگاه** | دسترسی کامل به تمام بخش‌های سیستم |
| استاد | *(فاز بعدی)* |
| هنرجو / والدین | *(فاز بعدی)* |

## ۴. مشخصات کلیدی حوزه کسب‌وکار (Business Rules)

### ۴.۱ انواع کلاس
سیستم باید از ۴ نوع کلاس پشتیبانی کند:
1. **خصوصی** — یک هنرجو، یک استاد
2. **گروهی**
3. **نیمه‌گروهی**
4. **تمرینی**

### ۴.۲ الگوی زمان‌بندی
- کلاس‌ها می‌توانند **تکرارشونده (هفتگی/ترمی)** باشند — یک‌بار تعریف، تولید خودکار جلسات آینده.
- یا به‌صورت **جلسه‌به‌جلسه (Ad-hoc)** باشند — هر جلسه جداگانه ثبت می‌شود.
- سیستم باید هر دو مدل را همزمان پشتیبانی کند.

### ۴.۳ مدیریت اتاق/فضای فیزیکی
- آموزشگاه چند اتاق فیزیکی دارد.
- سیستم **باید تداخل زمانی اتاق‌ها را تشخیص دهد** (دو کلاس نباید هم‌زمان در یک اتاق باشند).
- به همین ترتیب، تداخل زمانی استاد نیز باید بررسی شود (یک استاد نباید هم‌زمان دو کلاس داشته باشد).

### ۴.۴ ساعات کاری و روزهای فعالیت آموزشگاه
- ساعات کاری: **۰۹:۰۰ تا ۲۱:۰۰** (هر روز فعال)
- روزهای تعطیل: **پنجشنبه و جمعه**
- سیستم باید هنگام برنامه‌ریزی کلاس، خارج از این بازه/روزها را رد کند (اعتبارسنجی سمت سرور).

### ۴.۵ قانون تخصیص استاد
- هر کلاس (حتی نوع گروهی) دقیقاً به **یک استاد** تعلق دارد.

### ۴.۶ خارج از دامنه فعلی
- محدودیت ظرفیت کلاس گروهی/نیمه‌گروهی فعلاً بررسی نمی‌شود (فاز بعد).

## ۵. استک فنی پیشنهادی

| لایه | تکنولوژی |
|---|---|
| فرانت‌اند | Next.js (App Router) + TypeScript |
| بک‌اند | Next.js Route Handlers / Server Actions (معماری Full-stack یکپارچه) |
| دیتابیس | PostgreSQL |
| ORM | Prisma |
| احراز هویت | Auth.js (NextAuth) |
| UI | Tailwind CSS + shadcn/ui |
| هاست | Vercel (اپ) + Neon/Supabase (دیتابیس) |

**دلیل انتخاب معماری Full-stack یکپارچه (به‌جای بک‌اند جدا):** با توجه به مقیاس کوچک پروژه و توسعه‌ی تک‌نفره، این رویکرد سرعت توسعه را بالا می‌برد و دیپلوی را ساده می‌کند، بدون اینکه اصول معماری تمیز (لایه‌بندی service/repository) را قربانی کند.

## ۶. محدودیت‌های پروژه (Constraints)

- **زمان:** کمتر از ۱ ماه برای رسیدن به MVP قابل استفاده
- **نیروی انسانی:** توسعه‌دهنده تک‌نفره
- **مقیاس:** حدود ۵۰ هنرجو، تا ۱۰ استاد، چند اتاق فیزیکی
- **کیفیت:** باید برای استفاده واقعی در محیط پروداکشن مناسب باشد (نه صرفاً دمو)

## ۷. نقشه راه کلی توسعه (High-level Roadmap)

با توجه به محدودیت زمانی (کمتر از ۱ ماه برای MVP-1) و کار تک‌نفره، مراحل به‌صورت فشرده و اولویت‌محور طی می‌شوند. مدیریت مالی به‌عنوان فاز مجزای MVP-2 بلافاصله بعد از تحویل MVP-1 آغاز می‌شود.

| فاز | خروجی | وضعیت |
|---|---|---|
| ۱. کشف نیازمندی و پروپوزال | همین سند | ✅ انجام شد |
| ۲. مستند نیازمندی‌های دقیق (SRS) + User Stories | سند مجزا | ✅ انجام شد |
| ۳. طراحی دیتابیس (ERD) — MVP-1 | دیاگرام + اسکیمای Prisma | ⏭️ گام بعدی |
| ۴. طراحی UX ساده (Wireframe صفحات کلیدی) | فقط صفحات حیاتی (نه فول دیزاین) | |
| ۵. راه‌اندازی اسکلت پروژه (Setup) | Repo + CI پایه + ساختار پوشه‌ها | |
| ۶. پیاده‌سازی MVP-1 | کد (ترم، هنرجو، استاد، زمان‌بندی، حضور و غیاب) | |
| ۷. تست و دیپلوی MVP-1 | نسخه‌ی زنده و قابل استفاده | |
| ۸. طراحی و پیاده‌سازی MVP-2 (مدیریت مالی) | فاز جدا، بعد از تحویل MVP-1 | |

> با توجه به فشار زمانی، فازهای طراحی (UX/ERD) را سبک و کاربردی نگه می‌داریم، نه مستندسازی سنگین.

- هر استاد به یک یا چند ساز مشخص محدود است.
- ساعات کاری آموزشگاه: ۱۶:۰۰ تا ۲۱:۰۰، تعطیل پنجشنبه و جمعه. ✅ تأیید شد
